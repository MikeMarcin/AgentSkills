# Verification and closeout

The designated integrator judges what evidence proves. Commands, reviewers and
worker completion are inputs, not automatic acceptance. A delivered report or successful command never approves acceptance.

## Verify the behavior

Check the bound milestone's assigned obligations and all exit criteria, including
its composed public path. Whole-card Done is neither necessary for a partial-card
projection nor sufficient for milestone acceptance. Follow
[Plan-first execution](milestone-plans.md) for completion and explicit context renewal.

Ordinary slices run focused changed-surface checks. Exercise the selected public
path when internal helper tests could pass while an acceptance claim stayed false.
Name the user entry point and the terminal observable result required by the claim:
opening a screen is insufficient when acceptance requires reading a file or reaching
a comparison. When false success is plausible, use a focused negative control that
removes the essential dependency or breaks the assertion and demonstrate failure.
For an installed/release claim, exercise that bundle with its actual test-only
features disabled. Choose these checks for the claim, not a universal test matrix.

Mutation-capable qualification uses the explicit disposable roots and live-state
comparison in [Qualification guard](qualification-guard.md). Record the limits of
that cooperative check; it cannot sandbox a native agent or authorize live edits.

Record actual outcomes, including failures, skips, incomplete commands and relevant
limitations. Required unavailable native or human evidence remains open.

Reuse passing checks whose relevant inputs are unchanged. Unrelated HEAD movement
is not invalidation. A fix reruns its affected checks. At a coherent integration
boundary, normally run one integration-focused pass for combined behavior. Broader
relevant suites/native checks resolve named scope/risk claims; an exhaustive matrix,
hermetic replay or repeated unchanged pass is not the default. Apply one concise
simplification review to touched code; a missing optional persona is not a blocker.

**Verified candidate:** each claimed behavior has direct relevant evidence and
known failures/limitations are explicitly classified against existing criteria.

## Review independently where it adds evidence

Use review when the user requires it or when it can discriminate a changed
persistence/migration, protocol, authority, concurrency, lifetime or destructive
risk. Choose the critical role for a named material risk instead of also running
ordinary review. A second review requires a distinct unresolved material concern
or an explicit request. Preserve existing route/fallback policy and use a native
reviewer when cross-provider review is unavailable.

Supply requirements, current bounded diff and concise check/evidence locations,
not the implementation transcript or a request to endorse its rationale. An
implementer is not its own independent reviewer. Findings block on demonstrated
failure of an existing criterion or critical changed-surface regression. Other
hardening or alternative designs are follow-up candidates. Reproduce/adjudicate
findings; corrections receive narrow rechecks, not a renewed whole-candidate loop.

**Review consumed:** material findings have evidence-backed dispositions and
required corrections are verified. Confidence alone cannot replace a direct test.

## Accept and commit

Use installed `references/bookkeeping.md` for actual claim/finish syntax and
acceptance files. Record criterion, outcome, actual revision and evidence; command,
observation, artifact and freeform evidence remain supported. Finish only accepted
work or the existing automated-complete/human-pending state. Maintain an empty
index where required, individual explicit paths and refusal/recovery guards.
Preserve unrelated changes and all permission/publication boundaries.

**Milestone accepted:** integrated behavior is demonstrated, no known critical
in-scope failure remains, and live records agree with the result. Otherwise return
the real partial, blocked or human-pending state.

## Close the RFC or pack

At the final RFC boundary, compare its scoped final diff to its immutable
RFC_BASE_SHA and account for every required card/criterion plus relevant in-scope
discoveries. Reconcile the RFC/index and run the configured structure gate, coalesced
for a pack where supported. Reuse unchanged evidence; full-pack closure is not
repeated after each milestone. Implemented and Auto-Verified remain distinct.

Keep required human/native gaps open. Record actual commits, limitations and
cleanup; remove only consumed task-owned temporary resources. Preserve partial
work and current handoffs. Local continuation is not authorization to push.

**Pack complete:** every required in-scope criterion is satisfied and the final
live closeout is truthful; otherwise report exactly what remains and why.
