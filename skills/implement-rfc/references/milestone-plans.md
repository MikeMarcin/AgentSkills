# Plan-first execution

The mandate bounds authorization; live requirements determine acceptance. One
adopted plan preserves grouping and default order. A card is an acceptance unit,
a milestone is an integrated outcome, and a generation is a native context.

## Execution owner

The selected recipe supplies the execution owner. Direct/native primaries use
`scripts/milestone_checkpoint.py bind/check` for shared obligation and exit checks;
its checkpoint/observation carries run, segment and mandate identity, selection,
repository state and plan binding, without a producer/dispatch identity. Preserve
selection in the existing continuation location. Common acceptance below applies to
all recipes; assignment/return, dispatch and integrator-renewal instructions apply
only to the coordinator-integrator recipe. A primary continues its session unless
interruption, an explicit request or its recipe requires recovery.

## Resolve and bind

Before implementation dispatch, use installed `scripts/milestone_plan.py discover
--repo-root ROOT --target ID` for a live RFC/issue, or `--source-root PACK` for raw
intake. `--plan` is relative to that source. Resolve explicit user intent, adopted
links, manifest/entrypoint pointers, root convention and known legacy documents.
Invalid, ambiguous, stale and unsupported inputs remain unresolved, never absent.

Pass the raw authored current group, outcome and exits to the first integrator.
It reserves/remaps IDs, imports, captures the baseline, adopts and implements in
the same context. `adopt --id-map FILE` uses the real relative source map. Preserve
packet provenance and LIVE_IMPORT. Interrupted linkage is stale; retry the original
source/map without replacing published provenance. Keep one live JSON under
`<rfc_root>/plans/<plan-id>/`; `MILESTONES.md` is a generated view. Card metadata
`milestone_plan: {id,path}` and RFC metadata/Markdown links support target-only resume.

After intake, `scripts/coordinator_handoff.py assign --repo-root ROOT --target ID`
with exact `--run-id`, `--dispatch-id`, `--producer-id`, `--mandate-revision`
computes the binding. `--milestone` selects an eligible group; accepted milestone
arguments are evidence facts from existing records, never inferred from Done cards.
Retain the returned assignment in existing continuation records. Helpers compute
fingerprints; users do not copy hashes manually. Human output is concise; `--json`
is explicit. Discovery/check/bind and stdout rendering are observational.

The binding covers consumer/branch, target, current definition, prerequisites,
source obligations and exits. Semantic coverage remains engineering judgment.
Look through relevant dependencies; claim only eligible cards and continue their
constituent work within one invocation. Workers may receive complete explicitly
authorized multi-card projections, but cannot select new work or own board/commits.

Legacy `needs-normalization`, absence and partial coverage call for bounded first-
integrator preparation followed by execution in the same context. Preserve supplied
intent and every selected obligation; expose excluded dependencies and unsupported
mechanical branches. Do not claim the helper normalized prose or proved semantic
coverage. No synthetic RFC, planner agent or extra approval ceremony is required.

### Adaptive preparation

The implementing engineer writes a bounded JSON proposal, preserving legacy stage
grouping and source intent. Run `prepare --source-root SOURCE --proposal proposal.json
--target ID --repo-root ROOT --json` before adoption. This is a read-only check,
not a Markdown parser. Retain its complete receipt beside the live plan in the
existing workflow records: legacy `source_evidence` includes the original text,
relative path and SHA-256. Keep the original source immutable. Adopt the proposal
explicitly with `adopt --source-root SOURCE --plan proposal.json`; its normal
source receipt identifies the normalized JSON. Both receipts are needed to trace
legacy intent. Later target-only discovery follows the adopted JSON once.

For absent plans, the same engineer defines the current outcome and executes it.
For partial plans, retain `unplanned_work` until decomposed. Use `check-amendment
--plan CURRENT --proposal PROPOSED --reason TEXT --source-basis TEXT` to check the
refinement before publishing it. This observational check requires unchanged scope
and plan identity, preserves all work selectors and exit text, and reports affected
milestones. It does not authorize changed requirements or publication. Whole-source
work cannot mechanically be replaced with a guessed criterion list. Reconcile such
requirement changes explicitly under the existing mandate.

`bind` and `inspect` accept a consumer-relative `--projection FILE` containing a
nonempty typed work list. Selection must be within the current milestone; original
exits and source definition identity remain bound. Narrowed completion applies only
to the projection, never its parent card, milestone or RFC. `inspect` also reports
transitive issue prerequisites, missing/unfinished and excluded prerequisites,
external dependency records, and unplanned work. These are observations for planning;
they do not claim eligibility, acceptance or permission to work outside the mandate.
Consult actual board eligibility before claiming work, including human-pending
prerequisites. Reuse relevant accepted evidence through the normal return contract.

Before publishing an amendment, reconcile affected active assignments and safely
renew their binding. Keep pending human/native decisions and their exact candidates
in continuation evidence; the plan never stores acceptance state. An unchanged
current definition with unchanged prerequisite/requirement fingerprints survives
future-only refinement. Recovery carries the same outstanding obligations after
writer quiescence and actual effects have been reconciled; it is not an amendment
that deletes unfinished work.
After a blocked or human-pending return, `independent-work` continuation may select
an independently eligible authorized milestone after safe release. Preserve the
pending candidate handoff; an unmet prerequisite cannot be bypassed by this reason.

## Complete and continue

V2 returns carry the exact binding, acceptance records for every obligation/exit,
evidence refs and explicit continuation intent/reason/detail/next milestone. Use
`coordinator_handoff.py check --repo-root ROOT --assignment FILE --return-file FILE
--execution STATE` with consumer-relative files and existing consumed/partial/accepted
observations. Current source projections are checked as well as fingerprints.
The helper checks consistency, never evidence truth or engineering acceptance.

Card completion, commits and headings are progress, not milestone boundaries.
Missing exits, shortened scope, affected requirements, stale/duplicate returns and
unknown writers cannot authorize new assignments. Execution observations cover
producer, descendants and commands; result arrival alone is not quiescence.

Continue the same integrator through constituent work, correction and useful partial
invocations with renewed dispatch authority. Normally request fresh context at a
substantial accepted boundary. A small related next outcome may request continue
with related-continuation reason and renewed scope. Context/availability recovery
may replace an unfinished producer only after effects and remaining obligations
are reconciled. No card-count, commit-count or heading replacement heuristic applies.

Keep the remaining authored plan unless material evidence warrants amendment.
Preserve unsatisfied obligations and user permissions. Future-only edits need not
invalidate unchanged current binding. Required human/native evidence remains open.
V1 logs stay historical; active plan-aware control needs scoped reconciliation.
Never hot-upgrade active assignments or treat rendered roles as observed loading.
