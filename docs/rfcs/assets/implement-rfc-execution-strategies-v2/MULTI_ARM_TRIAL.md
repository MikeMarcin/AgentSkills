# Matched real-code experiments with selectable arms

Status: not run. This protocol replaces the original D/O-only trial. It supports any explicitly selected strategies without requiring every catalog entry to run.

## Question

For the same real RFC outcome, which execution strategy delivers acceptable, maintainable code with less measured usage and human intervention?

The initial matched block has three arms: direct-astra-max, native-astra-ultra and coordinator-integrator-baseline. A planner-worker arm is available once its exact planner/worker routes and policy are frozen. Select it before running a four-arm block, or compare it with an incumbent in a later matched block. Do not append a new treatment after inspecting previous solutions and call the enlarged set a clean preregistered comparison.

A block is one fixed task/base/environment with one fresh implementation attempt per selected strategy. Repeat on distinct tasks or with additional independent attempts only under an explicit plan. A practical strategy comparison may change topology, routing, prompt procedure and context lifetime together. Label it as such. A later ablation can hold routes or concurrency constant; no one-factor causal claim follows from the initial three arms.

## Choose the task and common gate

Choose an owner-authorized, dependency-ready product-code task with a bounded integrated outcome and relevant direct checks. Exclude implement-rfc itself as the measured task. A possible source-grounded candidate remains a bounded pinned where-used reporting slice of RFC-MASK-0011, subject to checking the live state and prerequisites; the supplied MASK snapshot is older than the AgentSkills snapshot and does not prove present readiness.

Freeze selected requirements, authored milestone grouping/exits, relevant project conventions and permitted scope. All arms receive the same supplied plan. The strong planner may refine internal work orders but receives no special free plan authored after inspecting a candidate. Record how much solution detail the RFC already contains; a highly prescribed task tests execution under a plan more than novel planning.

Define the submission gate, acceptance commands, relevant performance checks and independent test fixtures before inspecting implementations. Held-out fixtures may test existing requirements, not introduce hidden requirements. Reuse source-baseline results for pre-existing failures.

## Freeze configuration without over-controlling the treatment

Record task/base/plan identities; skill and recipe bytes/revision; host version and selected surface; source/tracker/fixture roots; dependency/toolchain/hardware and cache policy; common prompt; scoped permissions; explicit route requests; effective host settings; judge routes; and budget/stop/repair policy.

Direct: request Astra Max and disable model-delegation tools through a supported scoped control; disallow alternate model invocation routes.

Native: request Astra Ultra with native delegation available. Exclude custom RFC roles/instructions and inherited user/global child-routing overrides where they would alter the intended native baseline. Keep ordinary host defaults unless a shared safety/budget limit is explicitly required. Record those defaults rather than inventing exact child routes or forcing a team. A clean native treatment need not emit a child.

Coordinated: freeze the actual current coordinator/integrator/leaf configuration and existing smallest-useful-team procedure. Do not upgrade models or compel more workers for the study.

Planner-worker: freeze exact planner and cheaper worker routes, feedback loop, product-edit ownership, concurrency and escalation/takeover policy. Route placeholders make only this arm unready; they need not block a separately selected three-arm study.

Check actual native support before product implementation. Documentation describes capabilities but does not certify the selected build/account. If an arm needs a different host/surface to run, record that as another treatment difference; do not call the comparison topology-only. Provider-side internals may not be pinnable; retain the host/version/date and actual observation limits.

## Budgets and stopping conditions

Use a common user-selected practical resource ceiling and an identical acceptance gate, with the units explicitly stated. Do not equate raw tokens across models/providers or assume turn caps are comparable across topologies. Where exact real-time spend enforcement is unavailable, call the ceiling advisory/checkpoint-enforced and retain overshoot; do not advertise a hard cap. Native permissions, credit purchases, resets and provider/account switching remain outside implicit authority.

Run each arm to its declared first-submission gate or budget/blocker boundary. Normal internal planning, iteration and permitted review count toward its cost. No best-of cherry-picking. Specify one bounded external-feedback repair episode for each arm, or another symmetric policy before any run. A cheap arm may finish early; do not spend its unused ceiling simply to equalize totals.

## Isolation

Prepare one distinct source branch/worktree per arm from the same exact base, plus separate build/test/runtime outputs. In personal mode, pair each source worktree with its own tracker worktree from the same committed tracker baseline. Preallocate/import shared task identifiers through authorized main/tracker mechanisms before branching. Preserve lane restrictions; duplicate candidate bookkeeping is not duplicate production delivery.

A Git worktree is not a security boundary. Exclude sibling refs/diffs, code, transcripts, solution memories and global per-project learning from each implementation's accessible scope where the host permits. Report cooperative-only controls where enforcement is unavailable. Share only declared immutable dependency caches; keep mutable outputs apart. Never clear personal memory, alter global authentication or delete user settings as a setup shortcut.

Use sequential runs on the same machine for the first pilot, randomized before execution, to reduce contention and account-measurement overlap. Across repeated blocks balance order. Record cache warming, resets, outages and other provider activity; do not claim provider caches can be forced identical. Keep the task's solutions hidden until every initial candidate is frozen.

## Initial candidate freeze

Capture the exact commit or a complete base-bound patch when a safe commit is unavailable. Save task-owned uncommitted effects and actual outstanding requirements. Account for native/owned writers and commands before candidate freeze; a final assistant message alone is not quiescence. Do not force custom RFC child receipts on native mode; use supported native lifecycle evidence and disclose missing observations.

Record compactions, replacement sessions, retries, failed dispatches, human nudges/approvals and any topology/route changes. Keep all attempts, including failures and deviations, under their originally assigned strategy with explicit flags. Also report adherence-qualified results where useful; never silently remove an expensive noncompliant run.

Native choosing no children is compliant. Ultra unavailable or custom-role leakage is a capability/adherence issue. Partial telemetry is an observability issue. None of these is interchangeable with product acceptance.

## Objective validation and blind Astra/Fable review

Run the same independent acceptance checks against every frozen candidate, in disposable output roots. Preserve candidate-authored tests as part of the product. Any newly discovered reproducer must correspond to an existing criterion and be applied consistently to every candidate where relevant.

Use neutral candidate IDs with a private treatment map. Supply each judge all selected candidates, the same requirements, relevant surrounding source and objective results. Hide execution traces, model/role names, usage, branch labels and self-promotional explanations from the quality view. Preserve unredacted originals separately. Audit bookkeeping independently; anonymization must not hide incorrect evidence or a product defect.

For the initial study use two independent fresh judge sessions: one Astra, one Fable. Each examines all three candidates and records per-candidate findings before a comparative verdict. Give them independently randomized/different presentation orders; across repeated blocks balance order. This is best-effort blinding and does not estimate all judge biases. Larger studies may use per-candidate sessions within an explicitly revised judge budget; no compulsory all-pairs debate tournament is needed.

Judges must distinguish existing-criterion failures, critical regressions, maintainability/architectural fit, test strength and relevant measured performance. Require file/symbol evidence and a reproducer where feasible. Permit ties, partial ordering and insufficient evidence; do not force a total ranking or turn aesthetic preferences into acceptance failures.

Freeze both quality verdicts before either sees usage or the other judge's verdict. Adjudicate disagreements with evidence; agreement is not proof. An optional bounded order-reversed check must be separately recorded rather than repeated until the favored answer appears.

## Repairs

After all initial submissions and quality verdicts are frozen, supply each arm only its own valid findings and reproducer packet. Never give it another candidate's code or design. Preserve its original strategy and budgeted repair policy. Recheck affected behavior and retain first/final candidates separately. Apply any genuinely new requirement equally only after declaring an amendment that changes the study's original scope.

Required independent review can be supplied by the authorized external review stage, but terminal production status still requires the consumer's engineering adjudication and any required human/native evidence. Trial acceptance is not live-main integration. Preserve unintegrated alternative branches and personal tracker pairs until explicit safe disposition; do not force a release helper whose integration preconditions are unmet.

## Usage and time

Reuse the existing usage capture, reconciled ledger and outcomes input. Join exact arm/attempt/session intervals; do not infer arms from role names. Count primary, planning, coordination, native/custom children, internal review, failures, repairs and recovery where attributable. Deduplicate native owning-response observations and avoid adding cache/reasoning subsets to parent totals or summing alternate overlapping totals.

Report each arm's initial usage and repair-inclusive usage to the common acceptance gate. Report elapsed time, human intervention count/time, relevant resource use, compactions/replacements, acceptance and coverage separately. For total elapsed time use start-to-gate, not sum of parallel child durations. Missing lineage does not erase known attributable usage.

Native observations may be complete per-response families, a trustworthy inclusive aggregate, partial records or unavailable. An authoritative inclusive total can support all-in cost even without a role breakdown; do not add visible children again. If aggregate semantics are unknown, retain it as a separate observation and do not claim an exact total. Quality can still be evaluated when economics are inconclusive.

Keep separate cost buckets: attributable arm work; shared external comparative review/validation; one-time study setup. A judge reviewing three candidates is a shared study cost unless finer attribution is supported. Publish total observed experimental consumption too. Excluding a necessary production review means a number is not full standalone delivery cost.

Subscription credit/window snapshots are separate measurements. Record provider/account/pool, timestamp, reset boundary, freshness, granularity, unrelated activity and observation lag. Do not convert tokens into quota percentages or infer a task debit from contaminated windows. API-rate equivalents use dated rates and are not subscription charges. Compare providers' allowances separately rather than adding arbitrary percentages.

Use experiment-specific arm/task identifiers for the outcomes adapter and retain the logical RFC/task link. Do not count three accepted alternatives as three production tasks delivered. An experiment manifest stores provenance, not a second mutable acceptance board.

## Decision and extension

First determine which candidates satisfy the common gate and what remains open. Then compare material engineering quality. Among materially equivalent accepted candidates, compare supported usage/time/human-burden measures. Where one is better but more expensive, state that tradeoff; missing data allows a quality verdict without an efficiency verdict. Do not invent a weighted mega-score.

One matched block provides a local result, not a universal topology law. Repeat on distinct useful task shapes before broad default changes: coupled engineering, separable work, and longer multi-milestone/resumed work. Adding another topology should need a recipe and a selected arm, not changes to the RFC bookkeeping or trial evaluator.

Keep the study tooling out of ordinary implementation context. No scheduled monitoring, automatic future reruns or live model launches are authorized by this document.
